# Troubleshooting Log

> Supporting document for
> [NETWORKWALKS-B082-WK1-PM1-CYBERSECURITY-LAB-SETUP](../README.md).
> Every issue is recorded as **symptom → cause → fix**, because that is the order
> you meet them in.

## 1. VM created with the wrong OS type (Ubuntu instead of Debian)

**Symptom.** The VM booted and ran, but VirtualBox's suggested hardware defaults did
not match Kali, and the VM details page reported `Ubuntu (64-bit)`.

**Cause.** Kali Linux is built on **Debian**, not Ubuntu. I selected Ubuntu in the
VM creation wizard because Kali was not in the dropdown list.

**Why it matters.** The OS type is not cosmetic — VirtualBox uses it to pick default
chipset, audio controller, graphics controller and Guest Additions behaviour.
A mismatch can cause subtle display and driver problems, and a reviewer reading the
lab report will notice it immediately.

**Fix.** Power off the VM (a full shutdown, not a saved state), then:

`VirtualBox Manager → KALI → Settings → General → Basic → Version → Debian (64-bit)`

## 2. Only 32-bit guest options available / `VT-x is not available`

**Symptom.** The VM creation wizard offers no 64-bit versions, or starting the VM
fails with `VT-x is not available (VERR_VMX_NO_VMX)`.

**Cause.** One of two things — hardware virtualisation disabled in UEFI/BIOS, or
Windows Hyper-V holding exclusive control of the virtualisation extensions.
On recent Windows 11 builds, Core Isolation / Memory Integrity enables Hyper-V
silently, so this appears even on machines where the user never installed it.

**Fix, in order:**

1. **Enable virtualisation in UEFI.** Reboot into UEFI setup and enable
   `Intel VT-x` / `Intel Virtualization Technology`, or `AMD-V` / `SVM Mode`.
   Confirm afterwards in Task Manager → Performance → CPU → *Virtualization: Enabled*.

2. **Disable Hyper-V on Windows.** In *Turn Windows features on or off*, uncheck:
   - Hyper-V
   - Windows Hypervisor Platform
   - Virtual Machine Platform
   - Windows Subsystem for Linux (if present)

3. **Disable Memory Integrity.** Windows Security → Device Security →
   Core Isolation → Memory Integrity → **Off**.

4. **Turn off the hypervisor launch type.** In an administrator PowerShell:

   ```powershell
   bcdedit /set hypervisorlaunchtype off
   ```

5. Reboot.

> ⚠️ Note that this trade-off is real: disabling Hyper-V also disables WSL2 and
> Docker Desktop's default backend. Re-enable with
> `bcdedit /set hypervisorlaunchtype auto` when you need them.

## 3. Plain NAT gave internet but no VM-to-VM path

**Symptom.** With Adapter 1 set to plain **NAT**, the VM reached the internet
normally, but planning ahead to a second VM there was no way for the two to
communicate. Both would receive `10.0.2.15`.

**Cause.** Plain NAT gives **each VM its own private NAT engine**. The VMs are not on
a shared segment; they are in separate, mutually invisible tunnels. Identical IP
addresses across VMs is the giveaway.

**Fix.** Created a **NAT Network** — a shared virtual switch that all VMs attach to:

`File → Tools → Network → NAT Networks → Create`

| Field | Value |
|---|---|
| Name | `NatNetwork` |
| IPv4 Prefix | `10.0.0.0/24` |
| Enable DHCP | ✅ |

Then attached the VM: `Settings → Network → Adapter 1 → Attached to: NAT Network`.

Full reasoning in [`NETWORK-MODES.md`](NETWORK-MODES.md).

## 4. No IP address inside the guest

**Symptom.** `ip addr show` lists `eth0` but with no `inet` line, and every ping
fails with `Network is unreachable`.

**Cause.** One of three things, checked in this order:

1. **Cable Connected** unchecked in Adapter 1 — the virtual cable is unplugged.
2. **Enable DHCP** unchecked on the NAT Network itself.
3. The DHCP lease was never requested because the interface came up before the
   network existed.

**Fix.** Verify 1 and 2 in the GUI, then force a lease renewal in the guest:

```bash
sudo dhclient -r eth0      # release
sudo dhclient eth0         # request a new lease
ip addr show eth0          # confirm a 10.0.0.x address
```

If the interface itself is down:

```bash
sudo ip link set eth0 up
sudo systemctl restart NetworkManager
```

## 5. Can ping 8.8.8.8 but not google.com

**Symptom.** `ping 8.8.8.8` succeeds; `ping google.com` fails with
`Temporary failure in name resolution`. `apt update` also fails.

**Cause.** Routing works, DNS does not. The two are separate layers — this is
exactly why the verification table tests them separately.

**Fix.** Check what the resolver is set to:

```bash
cat /etc/resolv.conf
```

If it is empty or wrong, either renew the DHCP lease (above) or set a resolver
temporarily:

```bash
echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf
```

> Note this file is often regenerated by NetworkManager on reboot. If the problem
> keeps returning, the DHCP server on the NAT Network is not advertising a DNS
> server — recreate the NAT Network with DHCP enabled.

## 6. `apt update` fails with repository or GPG errors

**Symptom.** `The following signatures were invalid` or
`Release file is not valid yet`.

**Cause.** Usually the guest's clock is wrong — a VM restored from a snapshot or
suspended for a long time can resume with a stale system time, which invalidates
repository signatures.

**Fix.**

```bash
sudo timedatectl set-ntp true
timedatectl status          # confirm the clock is synchronised
sudo apt clean && sudo apt update
```

## 7. Kali desktop is sluggish or stuck at a small resolution

**Symptom.** The desktop runs at 800×600 and will not resize; the window does not
scale when maximised.

**Cause.** Guest Additions are not installed, so the guest has no driver for
dynamic resolution.

**Fix.**

```bash
sudo apt update
sudo apt install -y virtualbox-guest-x11
sudo reboot
```

Then in the running VM's menu: **View → Auto-resize Guest Display**.

If the display is still slow, raise **Settings → Display → Video Memory** to 128 MB
and confirm the graphics controller is **VMSVGA**.

## 8. Black screen after the Kali installer finishes

**Symptom.** The VM reboots after installation and shows a black screen or returns
to the installer.

**Cause.** The installer ISO is still attached to the virtual optical drive and the
boot order prefers optical over hard disk, so the machine boots the installer again.

**Fix.** With the VM powered off:

`Settings → Storage → select the ISO under Controller: IDE → Remove disk from virtual drive`

Then confirm `Settings → System → Boot Order` lists **Hard Disk** above Optical.
